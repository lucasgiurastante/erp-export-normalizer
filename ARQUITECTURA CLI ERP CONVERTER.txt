Arquitectura: erp-export-normalizer
Núcleo: schema-driven, streaming, validación con reporte
input.txt ──► [detector] ──► [parser (schema YAML)] ──► [decoder/validator] ──► [transformer] ──► [writer]
                 │                    │                       │                    │              │
                 │                    └── formats/            └── converters       └── mappers     ├── JSON
                 │                                            (fecha/decimal/                     ├── CSV
                 └── auto-detect                               codepage/EBCDIC)                   ├── NDJSON
                                                                                                  ├── Parquet
                                                                                                  └── SQL inserts
Decisión clave: schema-first. No hardcodeas formatos. El YAML describe el archivo; el parser es genérico. Cada empresa tiene su variante de "JD Edwards fixed-width" — el schema ES el conocimiento portable.

Módulos
Módulo	Responsabilidad
cli.py	Entry, argparse, exit codes (0 ok / 1 error / 2 schema inválido)
core/schema.py	Carga/valida YAML (start, length, type, format, codepage)
core/parser.py	Corte de campos fixed-width / delimitado, streaming línea a línea
core/converters.py	fechas (YYYYMMDD→ISO), decimales (scale), codepages (CP850/EBCDIC→UTF-8)
core/validator.py	errores acumulativos (no corta en el primero), reporte con nº de línea
core/writer.py	JSON/CSV/NDJSON/Parquet/SQL
formats/	librería de schemas built-in (JDE AR, SAP batch, etc.)
plugins/	hooks para parsers custom (formatos binarios raros)
Reglas de diseño
Streaming — archivos de GB no caben en RAM. Procesar línea a línea.
Idempotente/determinista — mismo input → mismo output. Crítico para auditoría.
Sin red, sin DB — corre en entorno aislado (air-gapped). Esto es VENDEDOR.
--dry-run + reporte — valida sin generar, da conteo de registros/errores.
Schema 100% portable — un YAML compartido = mismo parser exacto en otra empresa.
format: jde_fixed_width
record_length: 44
codepage: cp850
fields:
  - {name: id,      start: 0,  length: 10}
  - {name: tipo,    start: 10, length: 15}
  - {name: fecha,   start: 25, length: 8,  type: date,    format: YYYYMMDD}
  - {name: monto,   start: 33, length: 8,  type: decimal, scale: 2, align: right}
  - {name: moneda,  start: 41, length: 3}
Usuarios: beneficiarios vs afectados
Beneficiados (en orden de valor)
Data engineers / BI — integran ERP legacy con Snowflake/BigQuery/Airbyte. Hoy escriben parsers ad-hoc que se rompen. Este tool = repetible, testeable.
Equipos de migración — salir de JDE/SAP viejo requiere exportar TODO a formato moderno. Fase 1 del proyecto.
Consultores de implementación — cobran por integración; tool gratuito = menos código a escribir, más margen.
Finanzas/reconciliación — auditoría limpia de exportaciones, validación suma=suma.
Pymes sin API — su ERP solo exporta .txt. Es su única puerta a modernidad.
Regulados (banca, salud) — necesitan trazabilidad: qué se convirtió, cuándo, con qué versión de schema.
Afectados/riesgo
Consultoras que venden converters propietarios — competencia directa gratuita. No es tu problema.
Uso incorrecto = pérdida de datos financieros — misparséate un decimal y los libros no cuadran. → De aquí nace la validación como feature estrella.
Regulados — necesitan garantías. → Beneficio: schema versionado + checksum + reporte = evidencia de auditoría.
Evolución en fases (cómo crece el impacto)
Fase 0 — MVP (2 días)
Fixed-width → JSON/CSV, schema YAML, tests, ejemplo. Impacto: devs individuales.

Fase 1 — Adopción (2–4 semanas)
Outputs: NDJSON, Parquet, Excel, SQL inserts
Auto-detección de formato por heurística (regex en header)
Biblioteca de schemas built-in (JDE AR/AP, SAP batch). Cada schema compartido = caso de uso nuevo sin código.
--report verbose con diagnóstico por línea
Impacto: equipos de datos completos. Aquí ya aplicas al programa OSS.
Fase 2 — Escala (1–2 meses)
Paralelismo/multiprocessing para GBs
Globbing batch, múltiples archivos
Generador de schema automático — das archivo ejemplo + guesses, infiere campos. Baja barrera de entrada drásticamente.
Integración Pandas/Polars (read_erp() → DataFrame)
Impacto: ETLs empresariales reales.
Fase 3 — Efectos de red (2–4 meses)
Registry central de schemas — comunidad comparte formatos. El tool vale más cuanto más schemas haya.
Reglas de negocio — validaciones semánticas (débitos=créditos, totales, referencias cruzadas). Esto lo convierte en infraestructura, no utilidad.
Checksums + resumen de conversión (evidencia auditoría)
Web UI para generar schemas sin tocar YAML
Impacto: nicho se vuelve "crítico". Dependen de ti.
Fase 4 — Ecosistema (6+ meses)
Airbyte/Singer source connector — entra en pipelines estándar del mercado
Conector a Databricks/Spark
Versión cloud/SaaS para no-dev
Schema marketplace (pago/patrocinio)
Impacto: estándar de facto para flat-file legacy.
Por qué este roadmap gana (y la aplicación OSS)
Cada fase sube el techo: dev → equipo → empresa → estándar.
Fase 3 es donde se gana el "hueco legal": validación semántica + registry = "ecosistema depende silenciosamente de esto". Eso es literalmente el pitch de Anthropic.
Las señales de credibilidad (CI, dependabot, schemas compartidos, issues reales) salen solas del desarrollo.
