## 1. DEV.to (tu artículo del 20 de agosto)

Ya publicaste *"Escaping the mainframe: converting legacy ERP flat files"*.
No escribas un artículo nuevo: ese ya tiene readership indexado y un
comentario. Con la v0.3.0 lo útil es un post de seguimiento corto, o editar el
anterior y añadir un párrafo arriba.

**Título:** What changed in erp-export-normalizer since August

**Texto:**

> Six weeks and forty releases after I open-sourced
> [erp-export-normalizer](https://github.com/lucasgiurastante/erp-export-normalizer),
> here is what actually changed, and what I got wrong.
>
> The short version: the first version could read a fixed-width file. Now it
> can read the things that made me start it in the first place.
>
> **Mainframe formats.** `type: packed` decodes COMP-3 BCD decimals.
> `PIC S9(7)V99 COMP-3` is 5 bytes with a scale of 2. Credit and debit
> suffixes work too, because that is how JD Edwards writes signed amounts:
>
> ```
> 1234.56CR  ->  Decimal('1234.56')
> 1234.56DB  ->  Decimal('-1234.56')
> ```
>
> I got the decimal point wrong on the first attempt. In `S9(7)V99` I read the
> `99` after the `V` as ninety-nine decimals. Only `(n)` repeats a position,
> so it is two. There is a test that says so, because I made the mistake once.
>
> **Copybook import.** The layout usually already exists in the client's
> COBOL source, so I stopped asking people to retype offsets:
>
> ```bash
> erp-normalize copybook CUSTFILE.cpy --output cust.yaml
> ```
>
> **Comparing two exports.** A file can pass every per-line check and still be
> wrong, which is why `crosscheck` and `diff` exist. `crosscheck` also takes a
> `references:<field>` check, so an invoice line pointing at a customer that
> does not exist fails the run instead of waiting for the accounting team to
> notice.
>
> **Bugs the tests found, not the users.** `JsonWriter` was buffering every
> row in memory while claiming to stream. A single undecodable byte raised a
> raw `UnicodeDecodeError` and killed the whole run instead of marking one
> field. That one came out of a property-based test, not out of a bug report,
> and it is the reason I now have 19 of them.
>
> **Still air-gapped.** No network, no database, PyYAML is the only
> dependency. That has not changed and is not going to.
>
> If you have a flat-file layout that has been passed down to you and nobody
> can explain, [open an issue with a sample](https://github.com/lucasgiurastante/erp-export-normalizer/issues/new?title=flat-file+layout%3A).
> I will turn it into a schema.

## 2. Reddit

**No lo publiques en r/Python ni r/programming.** Self-promotion allí está en
las reglas y un post que lo incumple se convierte enkarma negativo y, a veces,
en un baneo. La wiki de autopromoción pide que vendas el problema, no la
herramienta, y que vuelvas después con el resultado.

En communities donde sí se permite (r/dataengineering, r/ExperiencedDevs, o el
subreddit de tu vertical), la forma válida es responder a la pregunta de otra
persona. Copia el bloque de abajo en un hilo donde alguien se esteja peleando
con un fichero EBCDIC.

**Respuesta a un hilo (no abras post):**

> If the file is fixed-width and EBCDIC, two things bite people: the record
> boundaries, and the fact that `cp037` and `ebcdic-cp037` are the same codec
> under different names in Python.
>
> I maintain a small tool for exactly this,
> [erp-export-normalizer](https://github.com/lucasgiurastante/erp-export-normalizer),
> and the part that might help even if you never install it is that the
> layout lives in a YAML file instead of in the parser. Offsets, codepage and
> field types in one place, so a schema can be shared between teams and
> reviewed like code. The COBOL copybook importer reads the `PIC` clauses
> directly if you already have a `.cpy`.
>
> Happy to answer questions about the format itself. I wrote a longer piece
> on the EBCDIC traps here: [link al artículo de DEV].

## 3. Hacker News

**No hagas Show HN todavía.** Show HN es de un solo uso: si lo publicas con
10 estrellas y 54 descargas, se hunde y no vuelve a funcionar. Además exige
texto en inglés y una nota con lo que aprendió, no un anuncio.

**Cuándo hacerlo:** cuando tengas 200+ descargas mensuales o 2 o 3 personas
que hayan abierto issues de verdad. Son los umbrales que Anthropic puso para
su programa, así que sirven de referencia.

Si decides intentarlo, el formato de HN es: **el problema, no la herramienta**,
y en inglés.

**Title:** Show HN: I kept rewriting the same EBCDIC converter, so I made one

**Texto (rough, para pulir antes):**

> Every company over about twenty-five years old has the same thing in a
> closet: a fixed-width export from an ERP nobody wants to talk about. No
> delimiters, no header, codepage nobody remembers, and the layout documented
> in a COBOL `FD` clause that last changed in 1994.
>
> I kept rewriting a converter for these, so I stopped. The parser is generic
> and the layout lives in a YAML file, which means a schema can be reviewed
> like code and shared between companies.
>
> The parts that turned out to matter more than I expected:
>
> - **Determinism.** The same file and schema give the same bytes, every run,
>   with any number of workers. When the output is an audit artifact, "we
>   converted it" and "we can prove we converted it" are different claims.
> - **Memory.** Line by line, so a 5 GB file costs what a 5 KB one does.
> - **Every error, not the first one.** A broken layout gives you a report
>   with the line, the field and the raw bytes, not a stack trace on line 47.
> - **It reads the mainframe formats.** COMP-3 packed decimals, EBCDIC
>   overpunch, and an importer for COBOL copybooks.
>
> It is air-gapped on purpose: no network, no database, PyYAML only. The
> environments these files live in often cannot have either.
>
> The piece I would most like feedback on: I have a `--fail-on-empty` because
> an incremental extract that returns zero rows almost always means the feed
> broke, and a silent zero is the failure mode that costs the most. I am not
> sure that is the right default.
>
> Repo: https://github.com/lucasgiurastante/erp-export-normalizer

## 4. Stack Overflow y ServerFault

Aquí no se promociona nada. Se responde. Hay preguntas viejas sin buena
respuesta sobre EBCDIC y ficheros de ancho fijo en R, y el formato fijo es
precisamente el problema. Una respuesta útil con un enlace al final gana más
que cualquier post, porque la gente la encuentra buscando la respuesta.

**Para responder una pregunta de EBCDIC:**

> Two things that are easy to get wrong here. First, the record boundaries:
> VM/CMS and OS/360 fixed-format files carry no line separator at all in the
> data, because every record is padded to the same length. You read the
> record length from the DCB, not from the file. Second, the codec name: in
> Python `cp037` and `ebcdic-cp037` are the same thing, and which one your
> build accepts depends on how you spell it.
>
> If you want the parsing to be reusable, put the layout in a file rather
> than in the loop. That is what [erp-export-normalizer](https://github.com/lucasgiurastante/erp-export-normalizer)
> does; it is a small YAML with the offsets, the codepage and the field
> types, so two people parsing the same export get the same result.
